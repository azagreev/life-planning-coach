## Что нового в v1.4.2

**Тема:** Patch release. Фиксы из project-wide code review — gating-режим (BUG-018), test isolation (BUG-017), robustness release-тулинга (BUG-016), целостность артефактов и корректность данных в docs/методологии. Без новых фич; единственное поведенческое изменение — унификация порога on-track к 70%.

### Fixed

- **`scripts/release.sh` tag-шаг (signing) был env-brittle и валидировался слишком поздно** (BUG-016). Во время релиза v1.4.1 скрипт упал на шаге 6 (`git tag -a`) ПОСЛЕ необратимого шага 4 (`git push origin main`): `tag.gpgSign=true` + WSL-путь signing-ключа (`/mnt/c/.../id_ed25519_github.pub`), который не резолвится под MSYS/Git-Bash (`/c/.../id_ed25519_github.pub`), дал «unable to sign the tag» → half-shipped релиз, потребовавший ручного восстановления (ручной тег + Release через REST). Добавлены `_resolve_tag_sign_args()` + `_tag_dry_run()` (по аналогии с `_select_python()`, BUG-013): ремап WSL→MSYS пути ключа, fallback на UNSIGNED annotated tag если подпись объективно невозможна (прошлые теги тоже unsigned), и валидация создания тега среди preconditions через throwaway-tag dry-run ДО push — релиз больше не может застрять на полпути из-за signing/config mismatch. Regression-тесты: `tests/release/test_release_sh_signing.py`.
- **Полный test suite мутировал tracked `ROADMAP.md`** (BUG-017). `test_cmd_version_accepts_semver` вызывал `build-skill.py cmd_version` напрямую против working-copy: `cmd_version` штампует ROADMAP-строку `(released <today>)` текущей датой, поэтому даже «no-op» sync на текущую версию переписывал дату и оставлял `git status` грязным (`modified: ROADMAP.md`) после `python -m pytest`. Тест теперь гермитичен — копирует все 6 synced-файлов в `tmp_path` и `monkeypatch`-ит `PROJECT_ROOT`, sync гоняется только против tmp-копии; добавлен guard, что реальный `ROADMAP.md` остаётся байт-идентичным. Production-код не менялся.
- **`accept_backfill` ставил `full_persistence` без подключённого календаря** (BUG-018). При mid-session подключении Drive из `lean_conversation` (календарь не подключён) и принятии backfill скилл уходил в `full_persistence` — режим, который матрица §5 резервирует за drive + calendar. Дефект originated в источнике-схеме (`references/state_v2_schema.md` §6) и зеркалился в `scripts/gating_logic.py::accept_backfill` + операционном промпте `references/templates/AI_Instructions.md` §Backfill, а e2e-тест ассертил неверный `full_persistence` (зелёный тест охранял баг). Исправлено calendar-aware-логикой `full_persistence if previous_mode == execution_no_wiki else wiki_no_execution` — идентично уже корректному sibling'у `on_drive_connected_mid_session`. Production-сигнатуры не менялись. Тест приведён к корректному ожиданию (`wiki_no_execution` из lean) + добавлена ветка `execution_no_wiki → full_persistence`.
- **Integrity-фиксы из project code review** (целостность): (1) routing-ярлык Weekly Review «(7-step)» был устаревшим — модуль давно `9-step` (Step 8 Gap Analysis + Step 9 Lessons Learned); поправлено в `SKILL.master.md` и пересобрано во все 5 артефактов (`SKILL.md` + `platforms/*`). (2) Битая ссылка `USER_GUIDE_MCP_KIMI_CLI.md` в `references/platforms/kimi-cli.overlay.yaml` → реальный файл `USER_GUIDE_KIMI_CLI.md` (пересобрано в `platforms/kimi-cli/SKILL.md`). (3) `AGENTS.md` сам себе противоречил по release-тулингу: §4.2 называл `release.sh` deprecated, тогда как §0.2 (+ ROADMAP + BUG-016 hardening) фиксируют его каноническим orchestrator'ом, а §3.1 рекомендовал deprecated `sync-version.sh`. Приведено к консистентности: `release.sh` = entrypoint, `build-skill.py version` вместо `sync-version.sh`.
- **Data-correctness фиксы из project code review** (корректность данных): (1) JSON-контракт в `references/module_phase4_dashboard.md` показывал `wheel_of_life` плоской картой `{health:6,...}`, тогда как consumer (`life-planning-dashboard.html` читает `wol.current[id]`) и полная схема (`dashboard_guide.md` + `state_v2_schema.md`) ждут вложенную `{current:{...}, previous, targets, sphere_goals}` — следование плоскому примеру дало бы wheel со всеми нулями. Пример приведён к вложенной форме (`current`). (2) Dashboard `schema_version`: «Key Metrics» в `SKILL.master.md` называли контракт `v2.0.1`, тогда как сам контракт везде `2.0` (`module_phase4`, `dashboard_guide`, HTML) — «2.0.1» был ошибочной отсылкой к state-schema gating-сабверсии. Поправлено на `v2.0`, пересобраны платформы. (3) `references/premortem.md` ссылался на «AAR … шаги 8–11», хотя Weekly Review имеет 9 шагов (AAR = 8–9) — поправлено на «шаги 8–9».
- **Единый порог «успех/on-track» = 70%** (корректность данных, из project code review). Недельная execution-score шкала в `references/goal_architecture.md` была 85/65 (85%+ отлично, 65–84% good, <65% revise), что конфликтовало с квартальной OKR-планкой (70%, `module_phase2_goal_architecture.md`) и AAR-skip gate (`execution_score ≥ 70%` в `module_phase3` + `state_v2_schema` + `evidence_map`). Перекалибрована к единому 70%: ≥70% on-track, 50–69% можно улучшить, <50% пересмотр; «85% — порог значимого прогресса» → «70% execution score — порог on-track (= квартальная планка)». Канон OKR (Doerr: «не 100%, иначе цели слишком лёгкие» — уже зафиксировано); квартал и AAR-skip не менялись (уже 70%).
